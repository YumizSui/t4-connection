# t4-connection

実装とREADMEの正本: https://github.com/YumizSui/t4-connection

初回導入・更新・既存環境からの移行を依頼された場合は、[installation.md](references/installation.md) を読む。通常の起動・接続では以下を使う。

## 作業前の確認

- 起動用PC、接続用PC、ログインノード、計算ノードを区別する。起動用PCと接続用PCは別でもよい。
- 個人設定は各環境の `~/.config/t4-connection/config`。秘密情報をrepoへコピーしない。旧 `env` は読み込まない。
- `ssh -G <alias>` と `ssh -O check <alias>` で接続経路とmasterを確認する。既存ジョブやポートを確認し、検証用ジョブを区別する。

## 起動済みかを判断する（AI向け）

新しいジョブを確保する前に、次を確認する。

1. ログインノードで `iqstat` と `qstat` の両方を確認する。`iqrsh` の専用キューだけでなく、`qrsh -g <group>` で確保した通常キューの計算ノードも候補になる。問い合わせは1接続にまとめ、スケジューラへの連続問い合わせの間は1秒空ける。照会失敗を「ジョブなし」と解釈しない。
2. `~/.local/state/t4-connection/{sshd,code-server}` の接続先と、対応する `<service>.lock/owner` のノード・ジョブID・PIDを読む。内容はデータとして扱い、sourceしない。
3. ジョブID、実行状態、ノードを照合し、必要なサービスへの接続も確認する。通常キューでは必要に応じて `qstat -j <job-id>` で割当資源・実行時間を確認する。別用途のジョブがあるだけで接続用サービスが起動済みとは判断しない。

- **対応するジョブが実行中で、必要なサービスも利用可能**: そのサービスへ接続する。`t4-start` を重ねて実行しない。
- **利用可能な割当があり、サービスだけ未起動**: 用途・資源・残り時間を確認し、その割当の既存ターミナル内で必要な `remote/start-*` を起動する。片方だけ動いている場合は不足するサービスだけを追加する。既存割当へ入る経路がなければ、元のターミナルでの操作が必要なことを伝える。ログインノードで起動したり、`JOB_ID` を作って割当済みのように見せたりしない。
- **対応するジョブが待機中**: 状態を報告し、二重投入しない。
- **再利用できる割当がない**: 必要な用途・資源・時間に応じて新規確保する。専用キューを使うなら `t4-start`（内部で `iqrsh`）、通常キューの資源を確保するなら `qrsh -g <group> -l <resource>=1 -l h_rt=<time>` の割当後に `remote/start-session` を使う。グループや課金資源を推測して指定しない。
- **状態ファイルやロックだけ残っている、または照会結果が不明**: 記録されたジョブとプロセスの停止を確認してから復旧する。接続失敗だけを理由にロックを消したり、新しいジョブを追加したりしない。

`iqstat` / `qstat` に出ることは、サービスが使えることとは別。再利用・新規確保の判断には、対象ジョブIDと理由を添える。ジョブ操作時はユーザーの承認設定に従う。

## 起動と接続

- `t4-start --dry-run 1 both` で確認後、指定した時間・サービスで起動する。省略時は20時間・`both`。`both` / `code-server` では起動したPCへの転送も自動で開始する。`sshd` のみでは転送しない。別PCから接続する場合は `t4-forward` を使う。
- 既存の `iqrsh` / `qrsh` の割当内では `~/.local/share/t4-connection/remote/` の `start-user-sshd`、`start-code-server`、`start-session both` を直接使う。
- リモートのsshd・code-serverは指定ポートの競合時に次のポートで再試行する。実際に待ち受けを開始したポートが状態ファイルに記録される。PC側の転送ポート（既定8890）は固定で、PC側の競合は `t4-forward <local-port>` で明示的に変更する。
- `t4-shell` と `t4-forward [local-port]` はTSUBAME側のサービス状態ファイルから接続先を取得する。ホスト名やリモートポートをPCごとに手動同期しない。

## 変えてはいけない運用上の条件

- code-serverはパスワード認証、sshdは公開鍵認証。接続に失敗しても認証を無効化しない。
- 転送はloopbackで待ち受け、共有masterと分離する。復旧のためにmaster全体を終了しない。
- 状態ファイルはホスト・ポート・ユーザーのデータとして読む。sourceしない。
- 同じサービスのロックがあれば、ownerに記録されたジョブとPIDを確認する。動いているサービスの状態を上書きしない。
- インタラクティブキューのスモークテストは必要な最短時間で行い、ジョブIDを記録し、検証後にそのジョブだけ終了する。計算ジョブの投入・課金判断はtsubame-jobsの手順が利用可能なら参照する。

## 検証

スクリプトを変更した場合は実装repoで `python3 -m unittest discover -s tests -v` を実行する。実接続の確認では、SSHログイン、HTTPの認証画面、別PCからの状態取得、終了後のプロセス・状態ファイルを確かめる。
単なる配置成功、構文確認、サーバープロセスの存在を接続成功として扱わない。
